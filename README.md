# Учет дефектов вагонов

Платформа учета осмотров и дефектов грузовых вагонов в вагонном депо: REST API на DRF, PostgreSQL, Celery и Redis для фоновых задач, Telegram-бот, RAG на Gemini API поверх pgvector в PostgreSQL.

Инспектор регистрирует дефект прямо у вагона через Telegram-бота: фото, узел, тип, замеры, степень опасности. Система сразу прогоняет дефект через AI-анализ: модель смотрит на фотографии, находит нужные места в нормативных документах депо и похожие дефекты из истории, а затем выдает классификацию и рекомендацию по ремонту. Дальше инженеры и руководители ведут дефект до закрытия.

## Жизненный цикл дефекта

1. **Регистрация.** Инспектор проходит в боте пошаговую форму: вагон → цех → узел (список узлов зависит от цеха) → номер детали → тип дефекта → ответственный → фото → замеры → описание → степень опасности → вердикт → сводка. Форма живет в одном сообщении, которое редактируется на каждом шаге, поэтому чат не засоряется. На любом шаге можно вернуться назад или отменить ввод. Если заполнение прервется, недозаполненная форма сохраняется в Redis.
2. **Сохранение и AI-анализ.** Дефект пишется в базу, фото загружаются в S3-совместимое хранилище фоновой задачей. Gemini описывает фотографии, по описанию и данным формы ищутся фрагменты документов депо и похожие закрытые дефекты, после чего модель возвращает структурированный ответ: класс дефекта, уверенность, вердикт (допустимый (`OK`) / плановый ремонт / срочный ремонт / списание) и рекомендацию по устранению со ссылками на источники.
3. **Оповещение.** Если инспектор выбрал вердикт «списание», все инженеры и руководители получают в Telegram уведомление с кнопкой, открывающей карточку дефекта.
4. **Работа с дефектом.** Список «Открытые дефекты» → карточка → смена статуса `Открыт` → `В работе` → `Закрыт`. История изменений каждого дефекта хранится (`django-simple-history`).
5. **Пополнение истории.** Закрытый дефект векторизуется в фоне и становится прецедентом, для следующих анализов похожих случаев.

Если AI-сервис недоступен, сохранение дефекта все равно проходит: анализ деградирует до пустого результата и пишет ошибку в лог.

## Компоненты

Один Django-проект, три процесса: веб-приложение, Telegram-бот и Celery-воркер.

### Telegram-бот (aiogram 3, long polling)

Основной инструмент работы в цеху.

- **Новый дефект.** Пошаговая форма на aiogram Scenes, описанная выше.
- **Открытые дефекты.** Постраничный список, карточка дефекта и смена статуса с подтверждением.
- **AI-ассистент (`/ask`).** Диалог с моделью по документам депо: допуски, регламенты, ремонт, охрана труда. Отвечает со ссылками на источники; в контексте держится ограниченная история разговора.
- **Поддержка.** Сообщения пользователя пересылаются в группу операторов, ответы операторов возвращаются пользователю.
- **Привязка аккаунта.** Сотрудник связывает Telegram со своей учетной записью через одноразовый токен, выпущенный веб-приложением.

Состояние форм (FSM) хранится в Redis с TTL в одни сутки. События одного пользователя обрабатываются последовательно.

### Веб-приложение

Серверный рендеринг на Django с django-components, HTMX и Alpine.js, стили на Tailwind v4, сборка через Vite.

- дашборд: вагоны, открытые дефекты, вагоны с подошедшим сроком ремонта, сотрудники;
- реестр вагонов: добавление, редактирование, массовое удаление;
- списки дефектов, сотрудников и документов депо;
- личный кабинет: активные сессии, привязка и отвязка Telegram;
- аутентификация на django-allauth (вход по email, MFA) с защитой от перебора паролей (django-axes) и проверкой паролей по базе утечек;
- админка на django-unfold, через нее загружаются PDF-документы депо для RAG.

### REST API

DRF под `/api/v1/`: `wagons`, `employees`, `defects`, `measurements`, `photos`, `users`. Схема OpenAPI генерируется drf-spectacular, Swagger и Redoc доступны по `/api/schema/`. Права выдаются по ролям сотрудника.

### AI-сервис (Gemini + pgvector)

- **Индексация документов.** Загруженный PDF разбирается постранично (pypdf), режется на чанки по 2000 символов с перекрытием 200 (langchain-text-splitters) и векторизуется `gemini-embedding-2` в 1536-мерные эмбеддинги, которые хранятся в PostgreSQL через pgvector. Обработка идет в Celery, статус документа виден в админке.
- **Поиск.** Двухэтапный: сначала косинусный поиск в pgvector (top-20 кандидатов с порогом расстояния), затем переранжирование кросс-энкодером flashrank (`ms-marco-MultiBERT-L-12`). Модель реранкера запекается в Docker-образ.
- **Анализ дефекта.** Описание фото → расширенный запрос → поиск по документам и истории дефектов → генерация `gemini-3.5-flash` со структурированным выводом (Pydantic-схема).
- **Чат-ассистент.** Тот же поиск, ограниченная история разговора и потолок на размер контекста, чтобы стоимость запроса оставалась предсказуемой.

### Фоновые задачи (Celery)

- загрузка фото дефекта из Telegram в хранилище, с возобновлением после повторов;
- рассылка сообщений сотрудникам с повторами при сбоях и rate limit'ах Telegram;
- индексация PDF-документов и векторизация закрытых дефектов;
- отправка email.

## Роли и доступ

Роли сотрудников: рабочий, инспектор (дефектоскопист), мастер, инженер, руководитель.

- Инженеры и руководители видят и редактируют все дефекты.
- Остальные роли видят только те дефекты, которые осмотрели сами.
- Статус дефекта могут менять инженеры, руководители и инспекторы.

Правила видимости реализованы методами QuerySet'а (`visible_to`, `status_changeable_by`), и через них ходят и API, и бот, поэтому проверка доступа живет в одном месте.

## Предметная область

Справочники отражают реальную номенклатуру депо: типы вагонов (полувагон, платформа, крытый, хоппер, цистерна, думпкар, дозатор и др.), статусы вагона от прибытия до списания, виды ремонта (деповской, текущий, капитальный), цеха (автосцепка и тормоза, тележечный, колесный и др.) и привязанные к ним узлы: тележка, колесная пара, буксовый узел, автосцепка, тормозное оборудование и т. д. Дефекты делятся по типу (трещина, износ, деформация, излом, коррозия, течь, ослабление крепления и др.) и по степени опасности, к ним прикладываются замеры (длина, глубина, диаметр, зазор, угол…).

## Стек

| Слой | Технологии |
| --- | --- |
| Бэкенд | Python 3.14, Django 5.2, Django REST Framework, drf-spectacular |
| База данных | PostgreSQL 18 + pgvector |
| Очереди и кэш | Celery, Redis 8 (два инстанса: кэш и брокер/FSM) |
| Бот | aiogram 3, Redis FSM storage |
| AI | Google Gemini (google-genai), pgvector, flashrank, langchain-text-splitters, pypdf |
| Фронтенд | django-components, HTMX, Alpine.js, Tailwind CSS v4, Vite, TypeScript |
| Аутентификация | django-allauth (headless, MFA), django-axes, argon2 |
| Хранилище файлов | django-storages + S3-совместимое хранилище |
| Качество | pytest, Ruff, pre-commit, Prettier, djLint |
| Инфраструктура | Docker, Docker Compose, Gunicorn, WhiteNoise |

Redis разделен намеренно. Кэш работает с политикой `allkeys-lru` и без персистентности. Брокер Celery и состояние форм бота живут в отдельном инстансе с `noeviction` и AOF, чтобы под нагрузкой не потерялись ни задачи, ни недозаполненная форма дефекта.
